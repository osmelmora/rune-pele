# Native Rune view

A Rune app calls `rune_pele::Diagram::view` with Mermaid source and gets the diagram as native Rune elements: the same Scene the SVG writer reads, laid out with Rune's own text measurement and drawn as keyed shapes and text in Pele's paint order. All 33 types are drawn this way: the kinds `rune_pele::lower::NATIVE` lists. A palette or dark-mode change repaints without parsing, laying out or measuring again. `Diagram::view_with` tells the app when a link is pressed, and a tooltip shows where the pointer rests. Any other type, and a source whose Scene asks for something the lowering does not draw, is drawn by Rune's own `rune-mermaid`; any other failure comes back as an error.

## Sub-features

- `rune-snap` renders an example headless with Rune's `--snap`, in the system's light or dark theme: the `pie` example, and the `diagram` example for any Mermaid file.
- `rune-palette` switches the pie example's palette with its button, by a scripted tap or the `hues` scene.
- `rune-product` checks pie-pets through the public API at 1× and 2×: each slice's area against the Scene's angles and radius, ink in every label's box, a palette change with no layout, keys that survive an `idPrefix` and a value edit, a whole donut, an empty pie, and the `rune-mermaid` fallback.
- `rune-side-by-side` rasterises Pele's own SVG with resvg beside the native PNG and compares the pie's slice areas.
- `rune-graph` draws every corpus source of the 31 types it opens (every type `NATIVE` lists but pie) natively at 1× and 2× beside Pele's SVG through resvg, and holds each to three limits over the pixels that are not text.
- `rune-graph-product` checks one fixture of each opened type: a key per drawing that survives an `idPrefix` and a value edit, a palette change with no layout, the fallback and its reason, a link's event and a tooltip of every type whose Scene has them, a casing the pointer passes through, and a gantt chart's today marker set by `ViewOptions::now`.
- `rune-hairlines` sorts every pixel that tells a 1× drawing of a standalone type from Pele's by the stroke it lies on in the Scene's geometry: slanted or curved, level or upright, or none.
- `rune-scene-features` counts, over the corpus and every harvested source of the standalone types, why the lowering refuses a source and each feature it draws only approximately, and marks what the corpus never shows.
- `rune-lowering` checks each lowering on its own against analytic geometry and resvg: dashes, arcs, holes, translucent strokes, corners and ends, boxes, a turned shape, text anchors, weights, turned text, the outline behind a title, a group's opacity, an icon's built-in glyph, a group that moves and turns, a turned axis title against Pele's, and a sankey's gradients under the default id prefix.
- `rune-break` breaks fourteen lowerings one at a time and shows the feature test of each fail.
- `rune-gradient` draws sankey natively: its corpus sources beside Pele's SVG under the id prefix `pele`, which the view lays out under when the app gives none and under which Pele fills links along gradients, a palette change that recolours a gradient, and each link's tooltip where the pointer rests on it.
- `rune-census` counts what the Scenes of the graph types ask an interpreter to draw, over the corpus and every harvested source.
- `rune-perf` times layout, lowering and painting for the largest harvested source of each type and for stress cases.
- `rune-scene` checks the Scene's read model the Rune view is built on: paint order, keys, inherited style and palette resolution.
- `rune-theme` checks the series colours a source sets in its theme config, at a pixel of git's main branch label: the source's in `Palette::pele()`, and the palette's own in any other. It also checks how the side-by-side reads those colours from Pele's SVG, and a git commit's tooltip.

## How to get to it (user POV)

- An app calls `Diagram::new(id, FontCatalog::…)` once and `diagram.view(cx, source, ViewOptions::new(width))` in its view. `diagram.view_with(…, on_event)` also passes a plain function that hears `Event::Activate(link)`.
- `Diagram::status()` says who drew the last view, and `Diagram::fallback()` why it was left to rune-mermaid.
- `cargo run -p rune-pele --example pie` opens the pie window. Its button reads `Palette: Pele` or `Palette: hues`.
- `cargo run -p rune-pele --example diagram -- <file.mmd>` opens any Mermaid file. The line above the diagram says who drew it, and names the last link pressed.
- Both examples take Rune's tooling flags: `--snap <png>`, `--theme light|dark`, `--script <json>`, `--size WxH`, `--scale N`. The pie example also takes `--scene hues`.
- A crate user reads the Scene through `pele_core::Scene::paint`, `Scene::resolve_paints` and `Scene::unread_styles`. `cargo run -p rune-pele --example walk -- <file.mmd>` prints that walk.
- A gantt chart marks today at `ViewOptions::now(milliseconds)`. Without it, the chart takes the system clock when the view lays it out and keeps that time: the marker moves only when the view lays the chart out again for another reason, such as a new source, width or font epoch. An app that wants the marker to follow the day passes `now` itself, for example the start of the current day. Each new value lays the diagram out again, and the same value does not.

## Gotchas

- Pele fills a sankey link along a gradient only where the drawing has an id prefix of letters, digits, `_` and `-`. A view lays out under `pele` when the app gives none, and the side-by-side draws Pele's SVG under `pele` too, so both fill links along gradients. Pele's `render` with no `idPrefix`, as `pele parity` draws the corpus, fills every link in one colour. That is Pele's own drawing, not a missing gradient.

- Text on a series colour contrasts with that colour in the Rune view, by Pele's own luminance rule. Pele's SVG does so only where the source sets the series colour, so its `17%` on orange is white. That difference is intended. It is not a parity failure; parity is the SVG writer's, under `parity.md`. `DIVERGENCES.md` lists every such difference.
- resvg has no CSS variables, and reads neither the root's `font` shorthand nor a corner radius in a `style`. The side-by-side resolves each `var()` as a page with no CSS of its own would, sets the root's `font-size` from that shorthand, and moves `rx` from a `style` to the attribute. A raw `resvg` of Pele's SVG draws black shapes with square corners and a 12px title.
- A source's theme config can set its series colours (`git0`, `cScale0`, `pie1`, `xyChart.plotColorPalette`). Pele declares them on the SVG's root as `--pele-series-N`, and the side-by-side reads a variable the root declares as a page does, not its fallback. The Rune view draws them only in `Palette::pele()`. Any other palette wins over them, as `DIVERGENCES.md` says, so such a source in another palette differs from Pele's SVG by design.
- The side-by-side needs Arial or a metric-compatible face: Arial on macOS or Windows, or Liberation Sans on Linux. `RUNE_PELE_RESVG_FONT=<face.ttf>` names another face, such as the Inter Rune draws with.
- Without `RUNE_PELE_OUT`, the pie test writes to `out/verify/pie-rune/`, the graph tests and the lowering test to `out/verify/rune-graph/`, and the spike tests to `out/verify/rune-spike/`.
- An app's view lays out with Inter's widths, so a node is as wide as its Inter label. The graph side-by-side lays out with Pele's own metrics instead (`ViewOptions::pele_metrics`), so that every shape is where Pele's SVG has it, and leaves text out of the comparison. Text drawn in Inter then does not fit its Arial-sized box exactly. Never judge label fit from a side-by-side image.
- At 1× a slanted or curved 1 point stroke is drawn a little darker by Rune than by resvg, all along it. The first two limits are therefore held at 2× and only listed at 1×, where a drawing is held to a patch of at most 30 px. A 2× row over a limit is a defect.
- The corpus side-by-side is ignored in a debug build, where its 860 comparisons take many minutes, so `mise run check` does not run it. Run it with `--release`, as above. A run that reports `7 passed; 0 failed; 2 ignored` was a debug run and compared nothing.
- At 1× resvg draws a stroke one device pixel wide or thinner as a hairline, with no joins: a 1 point mitred corner has no tip there. At 2×, or at width 1.01, it draws the tip. The Rune view draws it at every scale, as SVG says. And resvg covers a pixel in quarters across, so an upright 1.5 point line at x = 681.88 is two equal greys there and 0.87 and 0.63 of the colour here.
- `break-lowering.sh` edits source files and puts them back. It touches each file as it does, because cargo goes by modification times and would otherwise keep the binary of the broken file. Do not interrupt it; if it is interrupted, `git checkout crates/rune-pele/src` restores the sources.
- An icon's box shows Pele's built-in glyph where Pele's SVG has one: architecture's `database`, `server`, `disk`, `internet` and `cloud`, and treeview's folder and file in every treeview icon box. Any other box is left empty, as Pele's SVG leaves it for its host. A flowchart with `fa:` icons shows no icons.
- At 1×, resvg samples a pixel's coverage on a quarter-pixel grid (tiny-skia's `SUPERSAMPLE_SHIFT = 2`). An architecture group's icon is 20 points across, so its glyph's level edges fall on eighths of a pixel, and resvg moves them an eighth. Rune covers them exactly. So the cloud's flat base shows a short red run at 1×, with the rows at 50% and 75% coverage in resvg against 62.5% and 62.5% here. Every edge falls on quarter pixels at 2×, which passes.
- zsh passes an unquoted `${x:+--scene $x}` as one word, and Rune ignores an argument it does not know. Write `--scene hues` as two literal words.
- A tap at `t: 0.1` needs a frame laid out first. The script runner provides one, so the tap finds the `palette` key.
